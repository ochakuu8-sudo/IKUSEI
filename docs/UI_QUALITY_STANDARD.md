## 1. 完了の定義

見栄えを実現する制作方法は[UI美術の分析と制作設計](UI_ART_DIRECTION.md)に定める。以下の品質検査は、構図・素材・完成見本の制作を代替しない。まず販売する作品にふさわしい画面の完成像を作り、読みやすさと操作領域はその完成像に合わせて調整する。
本作で目指す品質は「機能が動く」「絵がある」に加え、必要な情報が読め、迷わず操作でき、画面を移っても同じ作品として見えること。これは本作の制作基準であり、商業ゲーム全般の認証や販売成功を保証するものではない。

判定は **合格・不合格・未確認・対象外** の4種類。対象外には理由を付ける。未確認を合格扱いしない。変更に必要な測定と実画面の評価で判定し、総合点や平均点で欠陥を相殺しない。外観変更に無関係な機能試験を追加する義務はない。適用範囲は第6節で決める。

品質確認は実装作業の一部であり、ユーザーへ毎回承認を求める手続きではない。不合格なら既に依頼された範囲内で修正と再確認を続ける。仕様の変更が必要な場合だけ、その変更点を切り分ける。ユーザーの明示指示が本基準と異なる場合は、その適用範囲を記録する。

仮置きの人物・ストーリー・報酬は許容する。仮置きを理由に、標準ボタンの混在、読めない文字、画面の欠けを許容しない。検証専用の説明は検証モードに限り、通常プレイの画面に内部IDや制作手順を混ぜない。

## 2. 不変条件と対応画面

### 2.1 固定キャンバスと可読性

- ゲームの論理キャンバスは **1200×500、比率2.4:1**。変更には既存の合意に従う。
- サイズに応じて変えてよいのは、キャンバス内の情報配置、文字・操作部品の論理サイズ、詳細の開き方。ゲーム状態、判定、選択順を画面サイズで変えない。
- UIの基準値は、拡縮後の **画面上のCSS px** で測る。内部の指定が24pxであっても縮小後7.8pxなら7.8pxとして評価する。スクリーンショットの拡大や高DPIを合格根拠にしない。
- 画面収容だけを成功条件にしない。画面の余白に押し込むための文字縮小、条件の削除、判定や効果の変更は禁止。

### 2.2 画面サイズとプレイの継続

幅844px・高さ352pxは文字・操作サイズを評価するための基準であり、プレイを許可する下限ではない。小さい画面・縦向きでも1200×500のキャンバスを縮小表示し、そのまま操作できる状態を維持する。

**画面サイズや向きを理由に、ゲームを覆う案内・閉じられないダイアログ・入力の遮断を追加しない。** 読みやすさは配置や部品の改善で解決し、プレイを禁止して品質条件を満たした扱いにしない。向き変更・ブラウザーのバー・ズームによるサイズ変更でも進行を保持する。

| 試験サイズ（CSS px） | 期待する状態 |
|---|---|
| 1440×800、1280×720 | 通常プレイ。大画面の余白と文字の序列も確認 |
| 844×390、844×352 | 通常プレイ。小画面の文字・操作サイズの評価基準 |
| 390×844、800×304 | 縮小したゲームを表示し操作可能。遮断せず、サイズ変更で進行を保持 |

## 3. 共通の合否基準

| ID | 基準と合格条件 | 主な検証 |
|---|---|---|
| Q01 収容 | 必須メニュー・操作・判断に必要な文字の欠け、他要素による隠れ、意図しない横スクロールが0件。スクロール領域は明示し、最後まで到達できる。タイトルのメニューをスクロールで隠さない | 要素と祖先のクリップ・実クリック・画面確認 |
| Q02 文字 | 選択文・主要操作・主要数値は16px以上。条件・報酬・代償・状態名・説明本文は14px以上。日付補助や非必須の注記だけ12px以上。すべて拡縮後の下限。必要条件や回復制約を注記扱いして小さくしない | 実効サイズの測定・等倍で読む |
| Q03 コントラスト | 意味のある文字は4.5:1以上。本作では大文字の緩和を使わない。条件未達の選択文・理由も読める濃さを保つ。背景画像の明部でも満たす下地を用意する。状態を色だけで表さない | 配色・合成後の背景評価・画面確認 |
| Q04 操作領域 | 進行や選択を確定する操作は44×44px以上。タッチで使う全操作も44×44px以上。デスクトップの補助操作は32×32px以上。小画面・coarse pointerはタッチ基準を適用。操作領域の重複0件 | ヒット領域・中心と端のタップ・等倍確認 |
| Q05 部品統一 | ボタン、タブ、選択行、状態表示、ダイアログ、通知は用途別に共有した様式を使う。ブラウザー標準の外観の混入0件。通常・ホバー・フォーカス・押下・無効・処理中・エラーを定義する | 部品見本・使用箇所・実画面 |
| Q06 情報の序列 | 主操作が分かり、操作前に必要な条件と代償を確認できる。見出し、本文、補助文を区別する。装飾が判断材料を圧迫しない。意味を表すアイコンには名称を表示するか、タップとキーで同じ画面内に説明を開ける | 操作を知らないつもりで読み順を確認 |
| Q07 キー・タップ | Tabで自然に移動、フォーカスが見える、Enter/Spaceで一回だけ実行。無効理由はタップ・キーでも確認可能。詳細を開く操作と選択確定を分ける。Escapeで意図しない選択・精算をしない | 操作試験 |
| Q08 設定 | 最大文字・動きを減らす・濃い字幕でも収容を満たす。設定を閉じると元の位置へ戻る。文字設定の適用範囲を明示し、非適用部分もQ02以上にする | 設定前後・復帰の画面比較 |
| Q09 遷移 | 場面の背景・立ち絵・配色の関係を保つ。意図しない白画面や標準部品の露出0件。入力から100ms以内に押下・処理中などの反応を出し、操作を待たせる装飾演出は400ms以内。保存や読込の完了は反応開始と区別する。本文の文字送りは別扱い | 通常速度で連続操作・短い録画・計測 |
| Q10 状態保全 | 画面変更・詳細・設定・サイズ変更・連打・再読込で進行や報酬が重複しない。保存失敗は成功と表示せず、元の状態と再試行手段が残る | 既存の保存・ADV試験＋対象画面 |
| Q11 差し替え | 名前・本文・条件・報酬をデータで差し替えても同じ表示規則が働く。文字列や場面IDごとの特別CSSで検証用データだけ整えない | 第6節の長文・境界データ |
| Q12 提示の正確さ | 必要値・現在値・結果が共通判定と一致。ランクと経験段階を混同しない。現在値→結果値、即時変化→翌朝回復を区別する。実装都合の用語を操作説明に流さない | 状態と表示の照合・文章確認 |

Q02・Q04の数値は本作の採用基準。44pxの参考は[W3CのTarget Size (Enhanced)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)、コントラストの参考は[Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。本書だけでWCAG全体の適合を宣言しない。

下限844pxでは縮尺が約0.703のため、画面上16pxには論理サイズ約23px、44pxの操作には約63pxが必要。現行の小さな部品をそのまま縮小しても合格しない。必要に応じて配置を変える。

## 4. 画面ごとの必須条件

| ID・画面 | 合格する状態 |
|---|---|
| S01 タイトル | セーブなし／あり／移行通知あり／検証入口ありで、全メニューと通知が欠けない。続きからの有効・無効が分かる。新規開始の置換対象が分かる。検証入口を通常と区別しつつ、主要操作を押し出さない |
| S02 依頼一覧・詳細 | 3依頼のタイトル、報酬、体力、主要な代償を比較できる。名称と値の対応が分かる。受諾不可理由、成長の機会、ランク低下と紹介停止は詳細まで追える。受ける／戻すが安定した位置にある |
| S03 尊厳 | 三軸の名称・現在ランク・数値を比較できる。各軸の意味、現在の帯、次の低下境界、回復が同ランク内のみであることを1操作以内で確認できる。ランク0では回復不可と分かる。帯の境界とランク低下の不可逆性を誤解させない |
| S04 成長 | 4項目の名称・現在段階・経験・次段階までの量を1画面で比較できる。説明全文を毎回並べず詳細へ分ける。最大段階を示し、達成感を出す。尊厳と別の尺度だと分かる |
| S05 ADV本文 | 立ち絵、話者、本文、ログ・設定への入口が干渉しない。最大文字でも全文が欠けず改ページする。文字送り／本文非表示／メニュー復帰の操作が衝突しない |
| S06 条件付き選択 | 原則として直前の場面の背景・立ち絵を引き継ぎ、読みやすい下地に選択を表示。3択の通常データはスクロールなしで全選択文と条件を読める。4択以上・複雑な条件は単一の選択一覧スクロールを許容するが、件数と続きの存在が分かる。必要値と現在値を併記し、選択文を切らない。状態比較のため左右を交互にスクロールさせない |
| S07 結果 | 基本報酬・追加報酬・経験・段階上昇・尊厳低下・回復・関係変化・紹介停止が生じた場合に識別できる。変化が多い場合も主要結果と翌日への操作が消えない。保存完了表示は保存成功後だけ |
| S08 回想 | 共通の「回想」入口から、場面と実際の選択記録を分類して開ける。保存構造まで統合する必要はない。未解禁・記録なし・既読が分かる。再生後は元の分類・ページへ戻る。回想で本編を変更しない |
| S09 設定・確認・エラー | 同じ用途の部品と操作順を使う。音、文字、画面、データの分類が分かる。確認は対象と影響を説明する。通知で主操作を隠さず、長文エラーにも再試行・復帰先がある |
| S10 台帳・返済・結末 | 所持金・必要額・不足・確定結果を区別し、対象期間が分かる。確定と閲覧を混同しない。結果後の再開・タイトル・回想への導線が欠けない |

選択肢の必要条件はゲームの情報であり、達成のために隠さない。AND/OR・上下限・対象人物の全条件を読めるようにする。補助的な育て方の説明は詳細に分けてよい。詳細表示の開閉で選択順・可否・選択を変えない。

尊厳の意味は、貞操低下＝性への奔放さ、品位低下＝人としての扱いの喪失、威厳低下＝貴族としての名声の喪失。これを社会的信用の一軸へまとめない。尊厳が依頼抽選を担う方針を維持し、UI改善を理由に全ADVへ尊厳分岐を追加しない。

## 5. 美術面の判定

### 5.1 美術の合格条件

UI改善では、この節の仕上げを主な作業にする。操作試験の成功は美術評価の加点にしない。同じ全体画像で複数項目を評価してよく、項目ごとに撮影・画面巡回を繰り返さない。

| ID・観点 | 本作で求める仕上がり | 不合格の具体例 |
|---|---|---|
| V01 構図と主役 | 各画面の主役を決める。机では主人公と3通の依頼、成長では4項目の進み具合、ADVでは人物と会話、結果では得失が最初に目に入る。主役・主操作・補助情報に明確な強弱があり、視線が自然につながる | 背景に広い空白を残す一方で重要な数値を端に詰める。見出し・説明・操作が同じ強さ。立ち絵の顔を不要な窓で覆う |
| V02 世界観と素材 | 屋敷、手紙、手帳、封蝋、控えめな金装飾という美術方針を共有する。紙の厚み、縁、影の向き・柔らかさ、金の使い方に共通ルールを持たせる。装飾は同じ系統の素材・線で作る | 新画面だけ無地のWebフォームになる。紙・カードごとに影や枠の太さが違う。金枠や光沢を増やしただけで高品質扱いする |
| V03 配色と文字組み | 紫・金・紙色を用途で使い分け、強調色を主操作と重要な変化へ集中させる。見出し・会話・数値・補助文の書体、太さ、行間を役割ごとに統一する。数値を比較しやすく揃え、自然な折返しにする | 全要素が強調色。段階と経験が括弧付きの一続きの文章に埋もれる。同じ用途で書体・余白がばらばら。小文字で密度を解決する |
| V04 部品と細部 | ボタン、タブ、選択肢、状態行を作品の部品として描き分ける。同じ用途では形・余白・アイコン比率・配置を揃える。角、境界、切り抜き、画像の解像感まで確認する | 標準ボタンが混ざる。枠に文字が接近する。小さな部品だけ浮く。立ち絵や装飾の縁に不要な白線、拡大ぼけ、意図しない切れがある |
| V05 場面の連続性 | 本文→選択→本文で背景と人物の存在感が続き、選択が会話の一部に見える。依頼の開封・台帳の開閉は同じ速度感と動き方を使う。新しい演出は画面の目的に結び付ける | 選択時だけ管理画面へ飛んだように見える。画面ごとに演出の強さが違う。通常速度で仮の背景や部品が露出する |
| V06 成長と変化の表現 | 成長は段階・進捗・到達を一覧で感じ取れる。結果は増減の内容と重要度を視覚的に区別し、尊厳ランク低下は通常の微小変化と異なる重みを持つ。必要な演出は短く、動きを減らしても意味が残る | 数値を文章で足しただけ。主要な変化が説明文に埋もれる。小さな増減すべてに大きな演出を入れる |

単に暗い配色や飾り枠を使うだけでは、V01〜V06を満たさない。画面の目的に応じて構図を設計し、作品の世界観を持った完成画面として評価する。比率や余白を一律に固定するのではなく、同じ役割の箇所を揃える。

### 5.2 仕上がりの見本と確認

最初に変更の中心となる1画面を実装上で仕上げ、部品・配色・文字・余白の見本にする。必要なら性質の異なる画面をもう1つ使う。実装担当者がV01〜V06で自己確認して展開し、通常はユーザーの承認待ちにしない。ユーザーが提示した見本や修正指示がある場合はそれを優先する。

見本と追加画面を並べて確認する。各画面の目的による違いは許容するが、「後から追加した部分」と分かる品質差は残さない。通常は全体画像1枚と、疑問のある箇所の拡大で判断する。同じ画像を何度も読み直さず、不合格箇所を決めて修正する。

現行のメイン画面・依頼状・設定は美術方針の参照であり、無条件の合格画像ではない。既知の欠けや小さすぎる文字を正解画像として登録しない。スクリーンショット差分の基準更新には、改善理由と上の判定を添える。

評価を「きれいになった」だけで終わらせない。依頼なら得るもの・失うもの・確定する操作、選択なら必要条件・現在値・選べない理由、結果なら変化と次の操作を、各画面の表示だけから説明できることを確認する。実装者が知っている内部処理で説明を補ってはいけない。別の評価者による確認を行えた場合は、実装者自身の評価と区別して記録する。

## 6. データと状態の試験表

以下はレイアウト耐性を調べる検証データであり、ストーリーの執筆制限・本番人数・経験の最大値を新たに確定するものではない。

| 分類 | 最低限用意する状態 |
|---|---|
| タイトル | 保存なし／通常保存／ADV途中／移行通知／検証入口。新規開始確認と取消 |
| 依頼 | 3件同時、短題・40字題・20字人物名、金額0と999,999、代償なし・三軸同時・受諾不可 |
| 成長 | 4項目0／次段階直前／段階上昇／最大。説明120字。独立した新しい項目名へ差し替え |
| 尊厳 | 100、81→80、61→60、41→40、21→20、1→0、0の回復。45→60・60→60の同ランク内回復 |
| 選択 | 1・3・5・8択、選択文60字、説明120字、AND/ORを含む条件6個、全達成・未達混在・必須出口だけ有効 |
| 結果 | 変化なし・金銭のみ・四成長＋三軸＋関係＋紹介停止。値や通知を落とさず表示 |
| 回想 | 0・1・50件、未解禁、長い題名、本文→選択→本文を記録した再生、元の一覧への復帰 |
| 異常 | 保存失敗・再試行成功、読めない保存、途中台本不整合、画像／フォント読込失敗、長い通知 |

この表は利用する状態の一覧であり、毎回すべてを通す指示ではない。通常作業は次の最小範囲を使う。

| 変更 | 外観確認 | 機能確認 |
|---|---|---|
| 色・枠・影・素材だけ | 変更画面の代表画像。対比が変わる箇所の配色を確認 | 原則不要 |
| 文字・寸法・配置 | 変更画面を1280×720と844×390。長文または最大文字を必要に応じて1状態追加 | 重なり・クリップ・ヒット領域の測定。疑わしい操作だけ確認し、全ボタンを押さない |
| 共有部品の外観 | 実際にその部品を使う代表画面をまとめて画像確認。構造が同じ画面は代表例でよい | ハンドラ・フォーカス等が変わらなければ操作巡回不要 |
| 画面拡縮・案内 | 第2節のサイズをまとめて測定・撮影 | 向き変更と復帰を代表経路で1回 |
| 遷移・操作・条件・保存 | 変更画面と必要な前後状態 | 直接影響する既存試験と代表経路を原則1回。経路が同じなら複数サイズで反復しない |
| 台本のみ | 変更した最長の本文・選択・結果を必要なサイズで確認 | 条件・報酬を変えた場合のみ追加 |
| 文書のみ | 文書の差分と参照先 | ゲームの起動・ボタン操作・ビルドは不要 |

成功した試験を手動でなぞり直さない。再実行は失敗、追加変更、または具体的な未解決の懸念がある場合だけにする。詳細ログや全DOMの反復出力を避け、失敗箇所と結論を取り出す。画像取得のために毎回新規ゲームから進めず、既存の検証データで目的の画面へ直接入る。

一般公開時は、公開物の一致と起動を確認する。配信経路や動作も変更した場合に限り、代表経路を1回確認する。同じ配信物の機能を公開前後で全件再試験しない。

商業版の出荷判定は通常の外観修正と別の作業として扱う。その段階でS01〜S10全体と上表の全分類をカバーし、PC Chromium系・Firefox・WebKitの代表経路、Android ChromeとiPhone Safariで横向き・タップ・セーフエリア・向き変更を実機確認する。エミュレーションだけなら「実機未確認」と記録する。これを毎回の軽微な修正の義務にしない。

全ブラウザー×全状態の総当たりは不要。ただし対応をうたう環境の試験結果を省略して合格にしない。機材がない場合は実装と可能な試験を進め、残る確認を明記する。

## 7. 検証の実装方法

### 7.1 既存試験との関係

`npm test` は状態・保存・条件の正しさ、`npm run test:ui` と `npm run test:adv-ui` は既存の操作・復帰の確認に使う。**これらの成功だけでは本基準の合格にならない。** 現状はタイトル全項目の収容、実効文字サイズ、タップ実寸、部品統一を網羅していない。

まとまったUI改善で `npm run test:ui-quality` を追加する場合は、画面の直接再現・まとめた画像取得・必要な寸法測定を中心にし、既存の操作試験を複製しない。今は存在しないコマンドであり、実装前に実行済みと書かない。小さな外観変更のために大きな検証基盤を先に作ることは求めない。開発用フィクスチャと保存は通常プレイから隔離する。

### 7.2 自動化するもの

- 対象画面・状態・ビューポート・文字設定を識別できる再現データと、変更前後のスクリーンショット。
- 論理寸法、実効文字サイズ、ヒット領域、必須操作の可視領域、選択文と条件の全文到達、スクロール末尾への到達。
- 条件可否、フォーカス移動、キー／タップ、詳細と決定の分離、再読込・保存失敗・連打後の一回性は既存試験を活用し、その処理を変更した場合だけ不足を補う。
- 共通部品の見本と使用漏れを検出する補助チェック。CSSクラスが付いているだけで外観合格にはしない。

DOMの存在や `isVisible()` だけでは、祖先に切られている文字や画面外のボタンを見落とす。画面内・祖先のclip・ヒットテスト・文字範囲と画像を併用する。回転した手紙の外接矩形同士が重なるだけで不合格にせず、実際の可視面と操作領域で確認する。

実効文字は一様拡縮なら `font-size × scale` で測る。部分拡縮や複数のtransformがある場合はそれを反映する。整数へ丸めて基準超過を作らない。

### 7.3 目視と遷移

画像・フォントが解決し、開封等の演出が完了した状態を等倍で見る。固定時間待ちだけに依存せず、画面準備完了を検出する。失敗・タイムアウトを「準備未完了だから対象外」で隠さない。代替画像・代替フォントでも操作が成立することを確認する。

遷移・演出を変更した場合だけ、該当部分を通常速度で1回確認する。色や枠の変更にゲーム全体の一巡を追加しない。「動きを減らす」での成功だけを通常演出の成功扱いにしない。開封中の半透明状態を完成後の配色不良と取り違えない。

### 7.4 証拠

[確認記録](UI_REVIEW_TEMPLATE.md)に、対象・根拠画像・結論を短く残す。小さな外観変更は同書式の簡易記録で十分。共通基盤の改修や出荷判定だけ詳細な環境表を使う。ローカル画像は後から追える場所へ保存する。記録のない合格、見ていないスクリーンショットの目視済み扱いは禁止。

## 8. 不具合の重さと完了・公開判定

| 重さ | 例 | 扱い |
|---|---|---|
| P0 | 進行不能、保存破損、選択や報酬の重複 | 対象の実装完了・通常の公開判定を通さず、先に修正 |
| P1 | 必須操作の欠け、対応画面で読めない／押せない、条件や代償の誤表示 | 対象の実装完了・通常の公開判定を通さず、先に修正 |
| P2 | 共通様式の不統一、余計なスクロール、迷う動線、演出の断絶 | 依頼範囲に含まれるものは完了前に修正。商業版では未解消0件 |
| P3 | 操作・理解を損ねない軽微な装飾差 | 場所・理由・次の扱いを記録。増え続ける場合はP2として統一を直す |

**一件のUI改善の完了**：対象Q/S基準をすべて合格、対象のP0〜P2なし、変更による退行なし。対象外の既知の問題は残件として記録し、ゲーム全体を合格と書かない。

**検証版の通常公開**：依頼範囲の完了条件と公開確認を満たす。対象外の既知の品質不足がある場合は、検証版であることと未達事項を記録する。ユーザーから未完成版を確認したい等の明示指示がある場合は、その指示に従い、公開した事実と品質合格を分けて報告する。

**商業品質の完了宣言**：全画面のP0〜P2が0件で、必須試験に未確認がなく、第5節も合格。UIだけの合格を、作品内容・経済バランス・全端末対応まで完成した意味に広げない。

GitHubへのコミットとGitHub Pages公開は別。公開が依頼されているときは、検証したビルドを配信し、公開処理の成功、HTML・主要JS/CSSの一致、公開URLでの起動を確認する。代表経路の追加確認は第6節の条件に従う。文書だけの変更ではゲームを再配信しない。

## 9. 実装担当者の作業順序

1. 依頼内容から対象のQ/S基準、影響する共有部品、試験状態を選び、確認記録へ書く。
2. 現行の欠陥を再現し、画像を残す。画面の役割、主操作、判断材料、詳細へ回す情報を決める。
3. 共通部品と代表画面を整え、1280×720と844×390で実寸を確認してから関連画面へ展開する。
4. 対象の機能試験・品質測定・実画面確認を行い、不合格を直す。試験範囲を狭めて合格を作らない。
5. 第6節で選んだ範囲の確認結果を短く記録する。遷移や動作を変更した場合だけ、関係する経路を通常速度で確認する。外観変更を機能試験の巡回へ広げない。
6. 完了判定を行う。公開も依頼されていれば第8節の公開確認まで行い、合格範囲と残件を報告する。
