## 0. 本書の位置付け

本書は、ユーザーとの対話で合意した「ADV内の選択肢に条件を設ける」方針を、実装可能な単位へ整理したもの。

**第1章は対話で確認された方針。第2章以降は、その方針を実装するために本書で定める初期仕様・技術上の手順である。** 技能の種類や成長式など、まだ合意していない内容は第13章へ分離する。技術上の仮の型名・配置案・検証データを、完成版の確定コンテンツとして扱わない。

既存の依頼、主人公以外の人物、台本はシステム構築用の仮置きであり、本番の人物・依頼・物語を確定する根拠ではない。過去の対話で提案された人物名、技能の組合せ、章数、日数、エンディング案も、本書では採用を確定しない。

`old/` の文書は現行仕様として参照しない。既存コード内の旧企画書参照コメントも、その企画を再採用する指示ではない。現在の挙動はコードとテストで確認し、今後の変更は本書の対象範囲に限定する。

## 1. 確認された設計方針

### 1.1 ゲーム体験

手紙で依頼を受け、仕事をしてお金を稼ぐ。その過程で主人公と依頼主の状況・関係が変わり、次の依頼や物語につながるADVを目指す。

今回の中心構造は次のとおり。

```text
依頼を選ぶ
  → ADVで事情を知る
  → 主人公の技能・尊厳・関係によって選べる対応が変わる
  → プレイヤーが対応を選ぶ
  → 報酬・出来事・人物との関わりが変わる
  → 後日の依頼や物語が変わる
```

### 1.2 条件付き選択肢

1. ADV内に、技能・尊厳パラメータ・人物別の関係値を条件とする選択肢を設ける。
2. **条件未達の選択肢も、その場面では表示する。** 選択文と必要条件を読み、何を満たせば選べるか理解できるようにする。
3. 条件未達の選択肢は実行できない。見えていることと選べることを区別する。
4. 条件が活動動機になるようにする。「この選択をするために技能を育てる」「この関係を築く」「この立場を保つ」と考えられることを目指す。
5. 条件付き選択の結果は、追加報酬だけでなく、出来事・依頼ルート・後日の手紙などにも接続できるようにする。
6. 高技能などの条件を満たさなければ到達できない物語があってよい。**低技能でも同じ物語・同じ結末へ到達できることは保証しない。**
7. 条件を満たすことは、その選択肢が実行可能になることを意味する。条件を満たした選択肢を自動で選ばせたり、常に最善の結末と扱ったりしない。

技能を単なる報酬倍率・体力節約・選択の助言だけのパラメータへ縮小しない。また、ADV内の条件表示を、手紙段階の依頼解放だけで代替しない。

## 2. 初期実装の範囲

### 2.1 実装するもの

- データ定義によるADVの選択・分岐・合流・終了。
- 技能、三つの尊厳パラメータ、人物別関係値に対する条件判定。
- 必要値・現在値・未達理由を表示する選択UI。
- 選択結果による追加報酬、パラメータ変化、物語フラグの記録。
- 物語フラグを次の依頼の候補判定へ接続する最小機構。
- ADV途中と結果画面を復元できる保存。
- 未選択分岐を飛び越えないスキップ、進行を変更しない回想。
- 本番コンテンツと分離した検証シナリオ、および対象を絞ったテスト。

### 2.2 今回まとめて変更しないもの

技能一覧・成長速度・全依頼の報酬、返済額、ゲームオーバー条件、章構成、人物設定、依頼の総数、画像制作、全体UIの再設計は対象外。

初期実装では、既存の基本報酬・消費・1日1行動の結果を保ち、その確定時点を分岐に対応できる形へ分離する。これは実装移行のための互換方針であり、完成版の日数や経済設計を再承認するものではない。

新しい会話エンジンや外部サービスを必須としない。既存の読書UI・画像表示を活かし、条件評価と進行の管理を分離する。

## 4. 条件判定の仕様

### 4.1 値の参照

| 種類 | 参照先 | 注意 |
|---|---|---|
| 技能 | 登録された技能IDの現在値 | 技能一覧・尺度は別データ。UIや判定関数へ名前を直書きしない |
| 尊厳 | `axes` の各軸の現在値 | 現行の `貞操`・`品位`・`威厳` を個別に扱う。合計値にしない |
| 関係 | 指定人物IDの現在値 | 場面の話者を暗黙の対象としない。依頼人以外を条件にしても対象名を明示する |

初期実装の「品位条件」は品位の現在値を参照し、`dignityCap` と混同しない。上限そのものを条件にする機能は今回追加しない。

### 4.2 比較と組合せ

- `min` は「以上」、`max` は「以下」。境界値を含む。
- 両方を指定した場合は閉区間の条件になる。
- 複数条件は `all`（すべて必要）または `any`（いずれか必要）で明示する。
- 条件なしは実行可能。空の `all` / `any`、上下限なしの比較、`min > max` は定義エラーとする。
- 尊厳などには「一定以上」だけでなく「一定以下」「範囲内」の条件も記述できる。高いほど必ず選択肢が増える判定に固定しない。
- 初期実装に確率判定・隠れた難度補正を入れない。表示した条件を満たせば、その選択は実行可能である。

### 4.3 判定時点

条件は、**その選択をする直前の論理状態**で判定する。第7章の作業中状態 `working` を使用する。

初回選択は受諾前の状態を基準とし、それ以前に確定した選択の効果があれば反映する。依頼終了時に与える基本報酬、関係上昇、技能経験、翌朝回復は先取りしない。

選択肢自身が与える技能・関係上昇によって、その選択肢自身の必要条件を満たした扱いにしてはいけない。先の選択で状態が変わった場合、次の選択では新しい値で判定する。

表示時と実行時は同じ純粋関数を使う。実行要求の受信時にも最新のセッション状態とリビジョンで再判定する。

### 4.4 条件と代償は別

「交渉2以上が必要」は参照条件であり、選ぶと交渉を2消費する意味ではない。「関係2以上」「威厳60以上」も同じ。

値の消費・増加、報酬、品位上限の変更は、選択結果の効果として別に定義し、表示も分ける。

初期実装では選択による追加の金銭支出・追加体力消費は入れず、既存の基本消費を維持する。後で追加する場合は、支払可能性と参照条件を別に評価・表示し、負の所持金や体力を黙って0へ丸めて支払済みにしない。

### 4.5 不正なデータ

未登録の技能ID・人物ID・軸、非有限値、範囲外の値、不正な型は「条件なし」と扱わない。定義時に検出し、実行時もエラーとして処理する。

新しく登録された技能について旧保存に値がない場合だけ、移行処理で登録済みの初期値を補う。IDの誤記を値0で隠さない。

## 5. データ構造

以下は責任範囲を示すTypeScriptの型案。名称や配置は変更可能だが、台詞文字列の解析、`eval`、UI内の場面ID別条件分岐で代替しない。

```ts
type SkillId = string;
type PersonId = string;
type NodeId = string;
type AxisId = "貞操" | "品位" | "威厳";

type ValueRef =
  | { kind: "skill"; id: SkillId }
  | { kind: "axis"; id: AxisId }
  | { kind: "relation"; personId: PersonId };

type Condition =
  | { kind: "range"; value: ValueRef; min?: number; max?: number }
  | { kind: "all"; items: Condition[] }
  | { kind: "any"; items: Condition[] };

// 必要な判定値と表示名・初期値・上下限はレジストリから取得する。
// ここで技能名や0〜100という共通尺度を固定しない。
type SkillDefinition = {
  id: SkillId;
  label: string;
  initial: number;
  min: number;
  max: number;
  unit?: string;
  growthHint?: string;
};

type ChoiceEffects = {
  bonusMoney?: number; // 初期実装は0以上。基本報酬に加算する。
  axisDelta?: Partial<Record<AxisId, number>>;
  dignityCapDrop?: number; // 0以上。現在値低下と区別する。
  relationDelta?: Record<PersonId, number>;
  skillDelta?: Record<SkillId, number>; // 成長式そのものは別途設計。
  storyFlags?: Record<string, boolean>;
};

type AdvChoice = {
  id: string;
  text: string;
  condition?: Condition;
  hint?: string; // 条件を満たすための行動ヒント。隠れた条件に使わない。
  effects?: ChoiceEffects;
  next: NodeId;
};

type AdvNode =
  | { id: NodeId; kind: "text"; lines: SceneLine[]; next: NodeId }
  | { id: NodeId; kind: "choice"; prompt?: string; choices: AdvChoice[] }
  | { id: NodeId; kind: "end"; effects?: ChoiceEffects };

type AdvScenario = {
  id: string;
  version: number;
  entry: NodeId;
  nodes: Record<NodeId, AdvNode>;
};
```

`SceneLine` は既存の話者・本文・場面ID・画像指定を活かす。新しい型を導入する際、現行の `PersonId` などを不要に別定義へ置き換えず、参照解決層で接続する。

初期シナリオは循環なしのグラフとする。分岐後の合流は可能。IDの重複、存在しない遷移先、循環、終了へ到達しない経路を検証する。反復する仕事は新しいセッションとして開始し、同じグラフ内の無制限ループで表現しない。

### 5.1 条件評価の戻り値

`evaluateCondition(condition, working, registries)` は、可否の真偽値だけでなく、条件ツリーに対応した表示情報を返す。

最低限、対象の表示名、必要な下限・上限、現在値、各条件の達成状態、`all` / `any` の結合関係、定義エラーを持つ。UI用に別の判定を重複実装しない。

### 5.2 物語フラグ

選択結果は、表示文ではなく安定したIDで記録する。例：`test.route.negotiatorAccepted = true`。

後続依頼には `requiresStoryFlags` / `forbidsStoryFlags` に相当する条件を持たせ、既存の人物解放・回数制限などと**ANDで合成**する。フラグがあるだけで既存の受注不能理由を無視しない。

初期実装では、選択が立てたフラグによって、検証用の後続依頼が候補に入ることまで実装する。NPC全般の状態管理、依頼の優先配信・保留期限の体系は別途設計する。

条件付きの分岐を見せるための入口依頼を、その分岐と同じ技能条件だけで閉じてはいけない。入口と分岐は別の判定である。そもそも別ルートに属する未訪問場面まで一覧公開する必要はない。

## 6. 選択肢UI

### 6.1 基本表示

到達した選択ノードでは、定義された選択肢を定義順で表示する。条件未達でも選択文を `???` に置き換えたり、非表示にしたりしない。初期実装に条件不足による非表示モードは設けない。

表示例は次のとおり。名称・数値は検証用であり、技能の採用案ではない。

```text
取引条件の交渉を任せてほしいと申し出る
  条件未達：交渉 2以上 ／ 現在 1
  選択した場合：追加報酬 100G

私的な相談として、詳しい事情を任せてもらう
  選択可能：依頼主Aとの関係 2以上 ／ 現在 2

今回は追加の話を引き受けない
  条件なし
```

複数条件は省略せず示す。「交渉2以上 **かつ** 関係2以上」と「交渉2以上 **または** 関係2以上」を区別する。ORの一方が未達でも、もう一方で選べることが分かる表示にする。

下限は「不足」、上限は「上回っている」など、比較方向に合う説明を出す。関係値には対象人物名を必ず付ける。

### 6.2 操作

- 条件未達の選択肢は読めるが、タップ・クリック・Enter・Spaceのいずれでも実行できない。
- 色だけで可否を表現しない。ロック状態、必要値、現在値を文字で示す。
- キーボードでもロック理由を確認できるようにする。例えば `aria-disabled` と説明テキストを用い、イベント側と進行側の両方で実行を止める。
- 選択表示中は背景タップによる本文送りと衝突させない。直前の文字送りキーの押しっぱなしで最初の選択肢を確定しない。
- ログ・設定・絵だけ表示から戻っても、選択位置と内容を保持する。ログの過去の選択を押して、本編を巻き戻さない。
- 二重クリックや複数入力を一回の選択として処理する。

### 6.3 画面と情報量

[AGENTS.md](../AGENTS.md) の1200×500固定キャンバスを維持する。選択時だけ専用の領域を表示してよいが、縦持ち専用レイアウトや全体画面の作り直しは行わない。

長い選択文・複数条件は折返しと選択領域内のスクロールで処理する。画面内へ押し込むために本文や条件を過度に縮小しない。ホバーだけで条件が分かる作りにしない。

既存の文字サイズ・動きを減らす設定を尊重する。条件の詳細と現在値は確認できるようにする一方、数式や内部フラグを通常画面へ露出させない。

### 6.4 条件と未来の見せ方

必要条件と、その場で約束される報酬・明示的な代償は隠さない。ただし、将来の場面名・結末・相手の秘密をすべて予告する必要はない。

`hint` は何を育てる・誰と関わるとよいかの説明に使う。成長方法自体が未設計なら「この仕事で育つ」と本番向けに捏造しない。

一度きりの場面で初めて条件を知る場合は、主に次周の動機になる。今周で再挑戦させたい依頼は、予告や返事の保留などをコンテンツ側で明示する。今回、全選択の再挑戦・無償取消は実装しない。

## 7. 受諾から依頼終了までの状態遷移

### 7.1 基本方針

受諾しただけで、未来の分岐結果や翌朝の回復まで本編へ反映しない。未完了の依頼を `activeSession` として保存する。

```text
机上
  → beginJob：受諾・セッション保存
  → ADV本文
  → 選択待ち
  → choose：条件再判定・選択記録・作業中状態の更新・保存
  → 分岐先の本文／次の選択
  → end：依頼の結果と日次進行を一度だけ確定・保存
  → 結果画面
  → acknowledgeResult：結果を閉じるだけ
  → 翌朝または章末精算
```

初期実装の依頼は一回の終了で一日進む。選択肢を一つ押すたびに日付を進めない。

### 7.2 セッションで保存する情報

- `sessionId`：同じ依頼の再受注でも新しくなる実行ID。
- `runId`、依頼ID、シナリオIDと版、受諾した章・日、セッションのリビジョン。
- `entrySnapshot`：受諾前の状態。循環参照を避け、セッション自身は含めない。
- `quote`：受諾時の基本報酬・体力消費・固定代償など。現行の割引や材料費を含む計算結果を固定する。
- `working`：受諾前の値へ、それまでに確定した選択効果を順序どおり適用した作業中状態。
- 現在のノードID、本文の行IDまたは行位置、文字位置。
- 選択済みノードと選択肢IDの履歴、適用した効果、到達した場面ID。
- `phase`：本文・選択待ち・結果表示などを区別する状態。

同じ本文を画面サイズに応じて改ページし直しても、選択履歴やノード位置は変わらないようにする。技能・尊厳・関係の条件欄は `working` の値を表示する。

### 7.3 受諾

受注資格、体力、進行状態を確認し、`quote` とセッションを保存する。基本報酬、基本の関係上昇、受注回数、日付はまだ本編へ適用しない。

セッション中は他の依頼、休養、章末精算を実行できない。タイトルへ戻る・再読込は中断保存であり、受諾取消ではない。復帰時はこのセッションを再開する。

### 7.4 選択

進行側は `(sessionId, nodeId, choiceId, expectedRevision)` を受け取り、現在の選択ノードに属する選択肢か、条件を満たすか、未処理かを検証する。UIから効果や遷移先を直接受け取らない。

有効なら、選択効果を `working` へ一度だけ反映し、履歴と遷移先を同じ保存に書く。保存が成功した後に、次の画面へ進む。

無効な要求は状態を変更せず、理由を返す。UIを経由しない呼出しでも、条件未達の選択は実行できない。

### 7.5 依頼終了と一度だけの精算

終端ノードに到達したら、次の順序で一つの保存結果を作る。

1. それまでの選択効果を反映済みの `working` を引き継ぐ。選択効果をもう一度適用しない。
2. 終端に定義された効果を一度だけ適用する。
3. `quote` の基本報酬・基本消費・固定代償・基本の関係上昇など、未適用の依頼効果を適用する。
4. 受注回数・人物解放・依頼履歴を更新し、既存の日次回復と日送りを一回実行する。威厳をその日に削ったかの判定には、基本代償だけでなく選択の効果も含める。
5. 完了済みの結果データ、差分内訳、選択履歴を保存し、`phase = result` とする。

初期実装では基本報酬を固定し、選択ごとの `bonusMoney` を加える。結果画面は基本報酬と追加分を分けて表示する。選択後の関係値から基本報酬を再計算しない。基本報酬の減額、前払い契約、追加の金銭・体力支払は別途設計する。

パラメータの上下限と品位上限低下は共通処理に集約し、プレビューと確定で一致させる。品位低下を選択効果と既存の上限低下関数で二重適用しない。

`acknowledgeResult` は結果表示を閉じるだけで、報酬・日付・関係を更新しない。結果画面の再読込からも二重精算しない。

### 7.6 選択のない既存依頼

既存の直線的な台本は、本文ノードと終端ノードへ変換して同じ流れで再生できるようにする。台本を書き直すことや全依頼へ仮の選択肢を付けることを必須にしない。

完了後のお金・体力・尊厳・関係・日付・返済状態は、同じ初期状態で旧処理を一回実行した結果と一致させる。変えるのは確定タイミングと途中保存であり、既存全体の収支ではない。

## 8. 保存・復元・例外処理

### 8.1 形式と移行

保存形式を新しい版へ更新する。次の版番号とキーは実装開始時の最新版から決め、v14の解析器へ新しい構造を曖昧に混在させない。

旧保存の所持金、残債、日付、三軸、品位上限、関係、受注履歴などは保持する。技能は登録された初期値、物語フラグは未達状態、セッションはなしで補う。新保存を読めない場合に旧保存へ黙って巻き戻さない。

**v14の保存は、ADVの再生前でも報酬・日付の更新が済んでいる場合がある。** 旧保存には再生位置がないため、移行時に直前の仕事を再受諾・再精算しない。保存されている更新済みの状態から再開する。

元の旧保存を削除しない。UI設定と既存回想も維持する。未採用の技能経験を過去の受注履歴から推測して付与しない。

### 8.2 途中復元

本文途中、条件付き選択待ち、選択直後、終了処理後、結果画面の各段階で復元できること。再読込によって現在値が受諾前や翌朝へ誤って切り替わらないこと。

セッションと日次状態は一つの論理トランザクションとして保存する。分岐記録だけ・報酬だけを別々に確定しない。

保存失敗時は未保存の次の画面へ進まず、直前の確定状態を保持して再試行を案内する。再試行で同じ効果を再加算しない。

### 8.3 更新後のシナリオ不一致

保存が参照するシナリオ版・ノード・選択肢が存在しない場合、先頭から自動再生したり成功扱いにしたりしない。

シナリオ版を保持して再開するか、明示的な移行対応を行う。初期実装で対応不能な未完了セッションは、理由を表示し、ユーザーの確認で `entrySnapshot` へ戻す救済を用意してよい。完了済み結果をこの救済で巻き戻してはいけない。元の保存はバックアップする。

## 9. スキップ・ログ・回想

### 9.1 本編のスキップ

通常スキップ・既読スキップは本文だけを送る。**未決定の選択ノードでは必ず停止する。** 以前の周回で同じ場面を読んでいても、自動選択しない。

選択待ちで `onDone` を呼んで依頼終了へ飛ばさない。ログや設定を開閉しても選択は確定しない。

### 9.2 到達記録

未選択の枝の場面を回想へ登録しない。受諾時にシナリオ内の全場面IDを一括で解禁しない。

場面IDは必要に応じて枝ごとに分け、既読判定も未訪問の枝へ波及させない。選択文を見ただけで分岐先が既読になることはない。

### 9.3 回想

回想はそのプレイで到達した枝、または保存された選択経路を読み取り専用で再生する。現在の本編パラメータで過去の選択を再判定しない。

回想の再生・終了・スキップによって、本編の所持金、技能、尊厳、関係、物語フラグ、日付を変更しない。既存回想の再生を維持する。

回想保存は本編と別領域でもよいが、同期失敗時は本編の確定記録から到達IDを冪等に再同期できるようにする。本編の報酬を再実行して回想を復旧しない。

## 10. 進行不能と条件設計の区別

初期実装の各選択ノードには、条件に左右されず進める選択肢を最低一つ用意する。例えば「追加の話は断る」「今回は通常の仕事だけにする」などで、通常終了へ到達できるようにする。

**これは操作不能を防ぐ技術上の初期規則であり、高条件の物語を低条件でも見せる救済規則ではない。** 条件なしの選択から、条件付き選択と同じ依頼ルートへ自動的に合流させる必要はない。

すべての条件付き選択を上位互換にする必要はない。関係を深める道、高報酬の仕事へ進む道、現在の立場を使う道など、異なる結果を作れるようにする。ただし、全ルートの価値配分・最終結末は本書では確定しない。

条件は行為や役割の成立理由に対応させる。関係が足りないから「助けたいと思う」ことができない、といった内心の禁止より、「内情を任せてもらうには関係が必要」という表現を使う。

ゲームオーバー条件の追加や変更は今回行わない。技術的な袋小路を、意図した物語上の失敗として扱わない。

## 11. 最小検証シナリオ

検証専用の依頼主Aと技能 `test_negotiation` を使う。本番の技能一覧・人物一覧へ採用する指示ではない。テスト／開発用データに隔離し、通常の依頼抽選へ混入させない。

### 11.1 初期状態と選択

基本報酬200G、基本体力消費20、尊厳の固定代償なし、技能の仮の尺度0〜3とする。値は機能検証用。

共通の仕事場面の後に、次の選択ノードを置く。

| ID | 選択の内容 | 条件 | 検証する結果 |
|---|---|---|---|
| `normal` | 追加の話は引き受けない | なし | 基本報酬のみ。専用の後続依頼は開かない |
| `negotiate` | 代理交渉を引き受ける | 検証用交渉2以上 | 追加100G、別の本文、`test.route.negotiatorAccepted` を立てる |
| `introduce` | 正式な紹介役を引き受ける | 威厳60以上 | 別の本文と別の後続フラグ |
| `confide` | 私的な協力者として任せてもらう | 依頼主Aとの関係2以上 | 関係を軸にした別の本文・後続フラグ |
| `alternative` | 今の立場に応じた別の役割を引き受ける | 威厳30以下 | 上限条件が機能する枝 |

別の小さな検証ノードでAND・OR・範囲条件を確認する。UIを見やすくするために、本番場面へすべての条件形式を同時に詰め込まない。

### 11.2 活動動機までつなぐ検証

同じ選択場面について、検証用交渉1の状態では条件文が表示され、代理交渉は選べないことを確認する。

検証用の経験獲得依頼を完了して交渉を2にし、もう一度到達可能な検証シナリオで、その選択が有効になることを確認する。これは成長・再挑戦システムの本番仕様ではなく、条件表示から値の変化までの接続テストである。

`negotiate` を選んだプレイだけで、完了後に検証用の後続依頼が候補へ入ることを確認する。別の選択でも同じフラグを立てて、分岐の差を消してはいけない。

## 12. 実装順序と受入条件

### 12.1 作業順序

1. 最新の `AGENTS.md`、対象コード、テストを再確認する。第3章の基準との差分を記録する。
2. 条件型、パラメータ参照レジストリ、純粋な条件評価、定義検証を作る。
3. シナリオのノード進行、選択処理、物語フラグをUIから独立して作る。
4. 受諾・進行・完了を分離し、セッション保存と旧保存移行を接続する。

7. 変更対象に絞って回帰確認し、実装済み範囲と未完了範囲を本書の状態欄へ追記する。

配置案は `src/adv/conditions.ts`、`src/adv/types.ts`、`src/adv/session.ts`、`src/ui/AdvChoices.tsx`。ファイルを増やすこと自体は要件ではないが、条件評価・状態更新・表示の責任は分離する。`src/` 全体の大規模な再配置は不要。

### 12.2 受入テスト

| ID | 確認内容 | 合格条件 |

## 13. 別途決める事項

以下は今回の実装で勝手に確定しない。

- 技能の種類・表示名・初期値・尺度・成長式・経験を得る仕事・周回引継ぎ。
- 各選択肢の本番条件値と、各尊厳軸の意味付けの追加・変更。
- 人物と依頼の本番内容、分岐数、報酬、結末。
- 返事の保留、再挑戦、重要依頼の予告・優先配信。
- 基本報酬を変更する契約、前金、追加の金銭・体力消費。
- 借金・期限・ゲームオーバー・全体の経済バランス。

これらが未確定でも、条件評価・表示・分岐・保存は検証用データで実装できる。完成版へのコンテンツ展開は、別途合意したデータを差し込んで行う。

## 14. 実装担当者への要約

> ADV内の選択肢に、技能・尊厳・人物別関係の条件を設ける。
> 未達でも選択文・必要値・現在値を示し、活動の目標にする。
> 選択結果を報酬だけでなく、物語と後続依頼へ接続する。
> 低技能でも同じ物語を見せることを必須にしない。
> 条件判定と値の消費を混同せず、受諾時に未確定の結果を先取りしない。
> 技能一覧・人物・バランスは仮例から確定せず、まず一つの検証シナリオを最後まで動かす。
