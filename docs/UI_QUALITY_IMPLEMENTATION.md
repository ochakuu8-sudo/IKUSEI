# UI品質改善の実装指示

2026-09-10。状態：**実装待ち**。[品質管理基準](UI_QUALITY_STANDARD.md)を具体化する最初の作業一覧。機能・保存の実装が済んでいることと、UIの品質が合格であることを区別する。

## 1. 今回の目標と制約

机・手紙・台帳の美術方針を活かし、追加した成長・選択・結果・回想を同じ作品のUIとして仕上げる。タイトルの欠けを直し、1200×500内の配置と実効文字・操作サイズを両立する。

尊厳ランク、回復、成長経験、依頼抽選、条件評価、選択順、報酬、保存形式はUI改善を理由に変えない。尊厳に応じてすべてのADVを書き分ける機能を追加しない。仮置きの人物・台本を本番へ書き直す必要はない。

新しいUI品質テストと共通部品も本作業に含む。実装言語やフォルダの移動を目的にした全面改修は行わず、画面を一巡できる単位で進める。

## 2. 先に作る共通部分

`src/DailyApp.tsx`の`c-button`、`src/ui/shell.tsx`の`button`、追加画面の生の`button`を確認し、現行の美術に合わせた共通操作部品へ集約する。対象は主操作、補助操作、アイコン操作、タブ、条件選択、一覧項目、状態行、通知、ダイアログ。

ボタンをすべて同じ形にする必要はない。用途ごとの違いを定義し、同じ用途で枠・余白・文字・フォーカス・無効状態を揃える。確認用の部品見本は開発専用に置く。エラー画面や回想の空状態も含め、通常のCSSを読み込んだ状態で確認する。

文字サイズ、色、間隔、操作領域、演出時間を共有の定義へまとめる。共有部品が従う値と実際の測定を結び付ける。新しいCSSを最後へ追記して偶然上書きする方法だけで仕上げない。変更した旧定義は適用箇所を調べて整理する。

UI-06の説明例は「威厳 ランク3／数値45、帯41〜60、40以下でランク2、回復は60まで、下がったランクには戻らない」。これは表示案であり、新しい上限状態を保存する仕様ではない。

UI-05で、存在しない背景を台本ごとに追加必須にしない。現在の場面情報を引き継ぎ、未指定・読込失敗時の代替表示を用意する。特定のデバッグ台本IDだけに対応させない。

## 4. 実装の順序

1. **現行の欠けの再現と測定**：UI-01〜03の失敗をフィクスチャ化し、変更前画像を残す。測定は論理サイズと実効サイズを区別する。
2. **共通基盤と代表画面**：部品・文字・小画面方針を実装。タイトルと依頼画面で最低サイズを満たすことを先に確認する。ここで関連画面の退行を確認する。
3. **成長と尊厳の情報整理**：UI-04/06。名前、段階、値、説明をデータから描画し、主情報と詳細を分ける。
4. **ADVの一巡**：UI-05と結果部分。受諾→本文→選択→分岐→結果→翌日を連続して確認し、表示変更が保存処理へ影響しないことを確認する。
5. **回想・設定・異常時**：UI-07/08。入口、戻り先、通知を揃える。
6. **品質判定と配信確認**：対象基準を実測・目視し、残件を記録。公開も依頼されている場合だけ、検証済みビルドのPages反映まで確認する。

最初の段階で小画面の要件を確かめる。最後に全体を縮小して済ませない。途中のコミットは可能だが、部分修正を全UI完成として報告しない。

## 5. テスト追加の作業内容

追加予定の`test:ui-quality`は次を担当する。現時点では未実装。

- 画面状態を再現するデータと入口を開発・試験専用に用意。再現値は本編保存に書き込まず、試験用保存領域を使う。
- Q01〜Q04/Q07/Q08に対応した測定・操作を登録。タイトル、成長、選択、結果、回想、エラー、サイズ不足案内を含む。
- 画像名に画面・状態・サイズ・文字設定を含め、測定値と一緒に保存。成功時も画像を残す。
- 既存の`test:ui`/`test:adv-ui`を保つ。新しい案内仕様で期待する画面が変わる箇所は、ゲーム進行の保持と復帰の検証に更新し、サイズのケース自体を削除しない。
- 最低サイズ、最大文字、長文、最後の選択肢、回想末尾、設定復帰を検証。失敗時には画面と原因を保存する。

既存の全経済シミュレーションは表示変更だけなら繰り返さない。条件や保存へ手を入れた場合は対応する状態試験を追加する。テストの都合で本番UIの挙動を変えない。
